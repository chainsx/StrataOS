# Build parameter audit

StrataOS does not treat "the recipe parses" as proof that a package can be
built. The builder applies a unified parameter policy to host tools, target
packages and the LLVM runtime, and runs layered checks both before and
after the real compile.

## Unified toolchain policy

Target C/C++ compilation must go through the wrapper in StrataOS's
toolchain directory. The wrapper fixes:

- `--target=<arch>-linux-musl`
- `--sysroot=output/toolchain/sysroot`
- `-fuse-ld=lld`
- `--rtlib=compiler-rt`
- C++ uses `-stdlib=libc++ --unwindlib=libunwind`

The build environment clears host search-path variables such as `CPATH`,
`C_INCLUDE_PATH`, `CPLUS_INCLUDE_PATH`, `LIBRARY_PATH`, `LD_LIBRARY_PATH`,
`PKG_CONFIG_PATH` and `CMAKE_PREFIX_PATH`. The target `pkg-config` can only
read `.pc` files inside the sysroot.

The LLVM runtime bootstrap uses a separate policy. Before linking the
libc++ shared library, the builder inspects Clang's `-###` output and the
real `link.txt` generated by CMake, requires LLD/compiler-rt, and rejects
`/usr/bin/ld`, `crtbeginS.o`, `crtendS.o`, `-lgcc`, `-lgcc_s` and
`-latomic`. The libc++ configuration also explicitly disables the GCC
runtime and external atomic library fallbacks. All `LIBCXX_*`,
`LIBCXXABI_*` and `LIBUNWIND_*` command-line variables are first looked up
in the current LLVM source's CMake files; version-obsolete variables that
do not exist in the source fail before configure runs.

## Four layers of checks

### 1. Offline recipe check

```bash
make audit
```

Checks every `packages/<name>/<name>.toml`:

- build-system and parameter syntax;
- package-owned `configure_args`, `build_args`, and `install_args`, including
  required option phases for audited special handlers;
- duplicate parameters;
- rejection of `-march=native`, `-mtune=native`, `-mcpu=native`;
- rejection of explicit links against libstdc++ or libgcc;
- whether the special handler explicitly passes the compiler, archiver,
  link parameters and parallelism parameter;
- the dependency graph and component ownership.

Results are written to:

```text
output/reports/build-parameter-audit.json
```

### 2. Upstream source option check

```bash
make preflight
```

This target downloads and unpacks package sources but does not start a
full compile. A normal `make` treats it as a prerequisite of `toolchain`,
so mismatches between a recipe and its upstream options are surfaced
before the long LLVM build begins. It directly checks:

- Autotools: whether options declared by the recipe exist in
  `configure --help`; total switches with a value are checked by switch
  name, e.g. GPGME language bindings must use `--enable-languages=...` and
  must not invent `--disable-lang-*`;
- Libassuan 3.0, libgpg-error 1.55 and libseccomp 2.6 do not declare a
  generic `--enable/disable-tests`; their test suites are controlled
  without running `make check`, and recipes must not invent that switch;
- CMake: whether the recipe's variables are covered by the source's
  `option()`, `set(... CACHE ...)` calls, or explicit custom cache setters
  that pass `CACHE`;
- Meson: whether options exist in `meson.options`/`meson_options.txt`, and
  whether boolean, feature and combo values are valid; feature defaults
  require `enabled`/`disabled`/`auto`, and legacy aliases are only accepted
  when upstream explicitly declares a deprecated value mapping;
- special handlers: whether the expected source files and directories
  exist.

The BusyBox special handler treats its native `scripts/kconfig/` as the
contract, and does not assume upstream provides the Linux-kernel-specific
`scripts/config`. Config fragments are merged directly into the output
directory's `.config`, and every requested value is verified after
`olddefconfig`, preventing an option from being silently disabled due to
dependency conditions.

This step cannot complete without network access. Official release builds
must not skip it.

### 3. Build-system probes

After host tools finish and before target packages begin, the builder
compiles minimal C/C++ programs directly through Clang, CMake and Meson,
covering:

- executables and shared libraries;
- pthread;
- C11/C++ atomics;
- libc++ locale, filesystem and thread support;
- LLD, compiler-rt, libunwind and the musl sysroot.

This step catches the case where "a parameter is written into a config
file but never actually picked up by the build system".

### 4. Artifact audit

After each target package is installed into its own DESTDIR, the builder
checks every ELF for:

- ELF architecture matching the target;
- a dynamic interpreter that is the target musl loader;
- no dependency on `libc.so.6`, `libstdc++.so`, `libgcc_s.so` or
  `libatomic.so`;
- RPATH/RUNPATH containing no host paths;
- `DT_NEEDED` dependencies that close within the final sysroot.

After configuration, the generated Autotools Makefiles, CMake/Ninja rules
and Meson/Ninja rules are scanned again to confirm that the real commands
reference the target compiler and contain no host `ld`, GCC runtime or
host multiarch library directories. Reports are written to:

```text
output/reports/generated-build-plans/<package>.json
```

The package cache fingerprint includes the recipe, the package builder and
the global build policy; BusyBox also includes its Kconfig fragment.
Changing a special handler or the global compile policy automatically
invalidates old package caches.

Each package's actual compiler, environment variables, configure/build/install
parameters, dependencies and parallelism are written to:

```text
output/reports/effective-build-parameters/<package>.json
```

## Limitations

Some source-level options are created dynamically by macros, platform
detection or generator scripts. Preflight can recognize projects like Expat
that wrap a CMake cache declaration in a `helper(VARIABLE DEFAULT CACHE
TYPE ...)` pattern, but it cannot cover every dynamic implementation. Some
configure probes must actually compile or run a test program. These checks
therefore push failures significantly earlier, but cannot replace full
native x86_64/arm64 builds and runtime verification.

## LLVM runtime bootstrap checks

The LLVM runtime bootstrap is audited separately from package recipes because it
builds libc++, libc++abi and libunwind before the normal target C++ environment
exists.

StrataOS keeps compile-only flags separate from linker-driver flags.  Linker
selection (`-fuse-ld=lld`), compiler-rt selection and unwind-library selection
must appear in generated `link.txt` files, but must not appear in generated
`C_FLAGS`, `CXX_FLAGS` or `ASM_FLAGS` compile rules.

CMake's `STATIC_LIBRARY` try-compile mode cannot prove that a libc symbol is
linkable.  StrataOS therefore inspects the target musl `libc.so` dynamic symbol
table and explicitly sets `LIBCXXABI_HAS_CXA_THREAD_ATEXIT_IMPL`.  The generated
CMake cache and compile definitions are checked before the long runtime build.
This prevents libc++abi from creating an unresolved strong reference to a libc
TLS-destructor function.

Any CMake warning that a manually supplied variable was not used is fatal for
both the runtime bootstrap and package builds.  This prevents obsolete or
misspelled options from being silently accepted.

### musl C++ runtime library policy

The LLVM runtime bootstrap forces only cache variables that are actually accepted by the selected LLVM source. It enables the pthread API and disables separate pthread, realtime and atomic fallbacks, then verifies the resulting cache before compiling. Removed LLVM variables such as `LIBCXX_HAS_C_LIB`, `LIBCXX_HAS_M_LIB`, `LIBCXXABI_HAS_DL_LIB` and `LIBUNWIND_HAS_C_LIB` are not passed. This avoids both false-positive static try-compile results and version-obsolete CMake options.

## Target libc++ header isolation

All target C++ invocations disable Clang's native C++ include discovery with
`-nostdinc++` and add only `output/toolchain/sysroot/usr/include/c++/v1` as the
standard C++ header directory. This prevents the headers bundled with the native
LLVM archive from being combined with the target musl libc++ runtime. The
toolchain stage verifies `__config`, `__config_site`, `cstddef`, and `locale`
before running a target C++ link smoke test.

## Autotools release archives

The source-aware preflight for Autotools recipes runs `configure --help`
directly from the release archive. The source manifest should point at an
upstream release tarball that ships a pregenerated `configure`, not a VCS
snapshot containing only `configure.ac`/`Makefile.am`. This means preflight
never needs to run `autoreconf`, and never implicitly adds Autoconf,
Automake, Gettext or Libtool bootstrap tools to the toolchain prerequisites.
procps-ng 4.0.5 therefore pins the SourceForge `procps-ng-4.0.5.tar.xz`.

### SQLite 3.50.1 autoconf bundle

SQLite's `sqlite-autoconf-3500100.tar.gz` uses a dedicated autoconf bundle
configuration interface. StrataOS only passes options that this bundle
actually advertises and that affect the target artifact:
`--disable-static`, `--enable-shared`, `--disable-static-shell` and
`--disable-readline`. `--disable-static-shell` makes the `sqlite3` CLI link
against shared `libsqlite3` instead of statically embedding the
amalgamation. BSD editline is off by default, so the redundant
`--disable-editline` is not passed; Tcl is not part of this autoconf
bundle's configuration interface, so `--disable-tcl` is not passed either.

### procps-ng 4.0.5 precise trimming

procps-ng is pinned to the official SourceForge release that ships a
pregenerated `configure`. The target recipe keeps shared `libproc2` and the
core monitoring tools, while disabling `kill`, `w`, `skill`, `pidof`,
`pidwait`, systemd and elogind support, all of which either duplicate
BusyBox or pull in extra login/service-management dependencies. 4.0.5 adds
`--disable-pidwait`; disabling it explicitly also avoids an unnecessary
`pidfd_open`/`__NR_pidfd_open` probe during cross-configuration.

### nftables JSON output

`nftables` is built with `--with-json` and an explicit `jansson` dependency
so the WebUI's Firewall CGI can query `nft -j list ruleset` instead of
scraping plain-text `nft list ruleset` output. `libmnl`, `libnftnl`,
`gmp`, `readline` and `jansson` are audited under the same generic
autotools/CMake layers as every other target package; no special-case
recipe handler was needed for any of them.
